# Phase 16 — Risk Register

Every risk below is grounded in the concrete audit findings in
`phase16_existing_system_audit_and_gap_report.md`. Likelihood/impact are
qualitative (Low/Medium/High), matching the evidence, not assumed.

| Risk | Likelihood | Impact | Existing mitigation | Missing mitigation | Owning phase | Acceptance test |
|---|---|---|---|---|---|---|
| Outdated model answers presented as current | High (no freshness classification exists at all today) | Medium-High | None — confirmed `MISSING` | Freshness/volatility classifier; route current-fact questions to `trusted_web` | 17/18 | A dated "who is the current X" fixture set must route away from `core_model` |
| Web misinformation surfaced as fact | Medium (no web search exists yet, so zero current exposure; becomes real once Phase 20 ships) | High | None yet needed (no web capability exists) | Official-domain filtering, cross-source agreement, source reputation scoring — all confirmed `MISSING` in Step 8 | 20/22 | Regression fixtures with known-bad sources must be excluded/flagged |
| Prompt injection via retrieved/fetched content | Medium (real filter exists for RAG/memory context today; will extend to a new content type — web/tool/MCP — that hasn't been screened before) | High | `core_model/rag/injection_filter.py` + `conversation/injection_guard.py`, real and wired for RAG/memory | Extend the same filter to cover web-fetched/tool/MCP content before Phase 20 ships any of them | 20/22 | Existing injection-fixture regression suite extended with web/tool-shaped payloads must still classify correctly |
| Malicious MCP server | Medium (only relevant if MCP is pursued; currently `MISSING`/not started) | High | None (nothing exists to mitigate yet) | Full evaluation of MCP's threat model before Phase 20 decides whether to build MCP support at all vs. direct connectors only | 20 | A decision record + (if pursued) a permission/sandboxing test suite before any MCP server is trusted |
| Source-rights violations (web/live evidence used without a rights basis) | Medium | Medium-High (legal/compliance) | The 16-dimension permission model (`dataset_verification_permission_service.py`) is real and strict (`training_use`/`commercial_use` never auto-approved) but is not yet extended to live web evidence | A lightweight rights/evidence-snapshot model for live web answers, distinct from the heavyweight dataset-verification-case model | 20/24 | No live web citation may be surfaced without a recorded evidence/rights basis |
| PII leakage (via memory, feedback, or a future knowledge-gap record) | Low-Medium | High | `core_model/conversation/memory_safety.py` (real PII/secret pattern gate on memory storage); dataset-ingestion-time PII detection (`core_model/corpus/pii_detection.py`) | A knowledge-gap record (Phase 19) must not be allowed to persist raw conversation content without the same PII-safety gate | 19 | Knowledge-gap capture must pass through the existing PII-safety check before persistence |
| Unsafe tool execution | Medium (no tool execution exists yet; risk activates once Phase 20 ships deterministic tools) | High | The Admin Assistant's `ActionDefinition(risk_level, permission)` pattern is a real, reusable template, but is not applied to chat-facing tools today | Action-specific permission model for chat tools (Step 6 finding: no live answer/search/fetch/tool/approval distinction exists today) | 20/22 | Every new tool must have a declared risk level and, for any mutating tool, a human-approval gate before Phase 20 ships |
| Language mistranslation | Medium (no translation provider exists yet; becomes real once Phase 21 ships one) | Medium | `text_normalization.py`'s protective-token guards (names/numbers/code/URLs) are a real, reusable pattern | Provider selection, quality evaluation, and the same protective-token guards applied to whatever provider Phase 21 picks | 21 | A protected-token regression fixture set (names/numbers/URLs must survive translation unchanged) |
| Tamil quality regression (from future training) | Low-Medium | Medium-High (core product value) | `tamil_quality_regression`/`tanglish_regression` categories already exist in `core_model/feedback/__init__.py::REGRESSION_CATEGORIES`, and `RegressionEvaluationService` is a real, working comparison engine | These categories are not yet wired into actual training-promotion gating (`training_suitability_service.py` has only a generic length check) | 25 | A promotion must be blocked if `RegressionEvaluationService` detects a Tamil/Tanglish-quality regression against the previous accepted checkpoint |
| Tanglish output leakage into public chat (when Tamil was requested/expected) | Medium (confirmed evidenced gap: current default policy is `tgl→tgl`, not `tgl→ta`, in the one real orchestration path that exists) | Low-Medium (UX/consistency, not safety) | `language_routing.py`'s classification is real and correct at input | The public-chat default output-language policy itself must be set explicitly in Phase 17/21, not inherited silently from the admin-diagnostic default | 17/21 | A Tanglish-input fixture must produce Tamil output by default for the public router, verified by a real test |
| Citation fabrication (model claims a source that wasn't retrieved) | Low (a real, working check exists) | Medium | `citation_validity_rate` + regex-based `[S#]` validation against the real evidence map already catches this in the one real orchestration path | Ensure whichever citation implementation is chosen as canonical (see duplication-prevention map) is the one wired into the public router — not a naive reimplementation that skips validation | 18 | Existing citation-validity test coverage must be preserved/extended, not bypassed |
| Knowledge-gap privacy (a gap record accidentally exposes private conversation content to reviewers/training pipelines) | Low-Medium (no registry exists yet — pure design risk) | Medium-High | Memory consent/capability-gating model (`resolve_effective_capabilities`) is real | A knowledge-gap record's schema must be designed to reference conversation content by policy-gated pointer, not raw copy, from day one | 19 | A gap record must never contain content excluded by the originating session's consent policy |
| Duplicate training pipelines | Low (this audit found none today, and produced an explicit duplication-prevention map) | Medium (wasted effort, drift) | This report's duplication-prevention map | Design review discipline for every future phase against that map | All (17-26) | Each phase's design doc must cite the duplication-prevention map and justify any new service |
| Latency (router adds a decision hop before every answer) | Medium | Low-Medium | The existing orchestration path's context-budget/generation flow is already the dominant cost; a lightweight deterministic router adds comparatively little | Explicit latency budget/target for the router decision itself | 18 | A router-decision-time regression benchmark |
| Provider outage (web/translation/tool provider unavailable) | Medium (once such providers exist) | Medium | The RAG failure→`insufficient_evidence` fallthrough pattern (Step 4) is a real, reusable model for graceful degradation | Apply the same pattern to web/translation/tool provider failures explicitly (Step 24's "operational event" classification) | 20/21/22 | A simulated-provider-failure fixture must degrade to an honest `insufficient_evidence`/clarify response, never a crash or silent wrong answer |
| Cost growth (web search / translation / tool calls are not free) | Medium (once those subsystems exist) | Low-Medium | The existing per-run/per-resource process-local lock pattern (Phase 15A) is a reusable concurrency-limiting template | Explicit rate/budget limits per provider, and observability (router observability is itself `MISSING` today) | 18/20/21 | A budget-exceeded fixture must degrade gracefully, not silently overspend |
| Approval bypass (a new phase accidentally lets an automated component approve/activate/release/roll back production) | Low (this audit found zero existing violations across all 71 Admin Assistant actions) | Critical | `BLOCKED_ACTION_SUBSTRINGS`, the propose→review→execute pipeline, and this audit's explicit verification (Step 13) that no action can self-approve production state | Every future phase's design must re-run this same verification against any new Admin Assistant action it proposes | All (17-26) | The Step 13 verification method (grep every `target_type=`/executor for production activation/rollback/release/approval verbs) must be re-run and pass before any new action ships |
| Production regression (a new phase breaks existing Phase 1-15A functionality) | Low (this audit ran the full 48-batch canonical regression live and changed zero application code) | Critical | The canonical regression manifest itself, the non-negotiable "never remove/rename/rewrite" rule this audit followed | Every future phase must extend the manifest with its own new batches and keep all 48+ existing ones green | All (17-26) | The full canonical regression manifest, re-run, with 0 new failures introduced |
