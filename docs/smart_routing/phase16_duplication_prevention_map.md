# Phase 16 — Duplication-Prevention Map ("Do Not Rebuild")

Every item below is a real, working, already-audited component (Steps
1-17). Phases 17-26 must extend or call these, never re-implement them.
This is a mandatory reference for every future phase's design review.

| Capability | Exact existing component | Where it lives | Do this instead of rebuilding |
|---|---|---|---|
| RAG ingestion | `backend/services/rag_ingestion_service.py` | RAG stack | Call it; do not write a second chunking/embedding pipeline for router-selected content. |
| RAG sandbox (trial-before-promotion) | `RagSandboxEligibilityService`, `rag_sandbox_index_service.py`, `rag_sandbox_retrieval_service.py`, `rag_sandbox_answer_service.py`, `RagSandboxEvaluationService`, `RagSandboxReportService`, `RagSandboxAcceptanceService` | `backend/services/rag_sandbox_*.py` | Phase 24's "knowledge-gap → RAG trial" bridge must call `RagSandboxEligibilityService.create_experiment()` (or equivalent existing entry point), not create a second trial pipeline. |
| RAG evaluation | `RagSandboxEvaluationService` reusing `core_model.rag.grounding_checks.unsupported_sentence_ratio` and `core_model.rag.injection_filter.detect_injection_signals` verbatim | `backend/services/rag_sandbox_evaluation_service.py` | Reuse the same grounding/injection primitives for any router-side evaluation; do not reimplement unsupported-claim detection. |
| Grounded generation | `backend/services/rag_generation_service.py` + `core_model/rag/citation_builder.py`, `grounding_checks.py`, `answer_policy.py` | RAG stack | This is one of two existing citation implementations (see below) — Phase 18 must pick one as canonical, not add a third. |
| Citation validation (2nd implementation) | `ChatOrchestrationService._assemble_and_generate()`'s inline `[S#]`-regex citation mechanism | `backend/services/chat_orchestration_service.py` | Phase 18 design decision required: consolidate onto one of the two existing implementations before building the router's own citation handling. Do not build a third. |
| Source rights | `ExternalDatasetPermissionAssessmentService` (16-dimension model; `training_use`/`commercial_use` never auto-approved) | `backend/services/dataset_verification_permission_service.py` | Any web-answer evidence rights concept must extend this model (or a deliberately lighter sibling), never a parallel rights system. |
| Sample quarantine | `ExternalDatasetQuarantineService` (isolated `0o700` per-import directory) | `backend/services/dataset_sample_quarantine_service.py` | Reuse the isolation pattern for any future untrusted-content staging (e.g. fetched web pages), do not invent a new isolation mechanism. |
| Training suitability | `backend/services/training_suitability_service.py` | Dataset/training chain | Extend with Tamil-specific checks (Phase 25) using the existing `REGRESSION_CATEGORIES` vocabulary (`tamil_quality_regression`, `tanglish_regression`, already defined in `core_model/feedback/__init__.py`) — do not create a parallel suitability service. |
| Dataset promotion | `backend/services/training_dataset_promotion_service.py` | Dataset/training chain | Any future "promote a trialed knowledge-gap answer to training data" flow must call this, reusing its existing contamination/leakage recheck, not duplicate it. |
| Incremental training | `incremental_training_execution_service.py`, `_run_approval_service.py`, `_comparison_service.py` | Training chain | Unchanged; Phase 25's re-test-after-training mechanism should reuse `RegressionEvaluationService.compare_runs()`/`create_improvement_report()`, not a new comparison engine. |
| Checkpoint evaluation | `incremental_training_checkpoint_acceptance_service.py`, `model_evaluation_service.py` | Training chain | Unchanged. |
| Model registry | Phase 14/15 model release/registry services (`production_model_release_*_service.py`) | `backend/services/` | Unchanged; Phase 26's "integrated production acceptance" reads from this, never re-implements release governance. |
| Canary | `production_model_canary_service.py` | Production governance | Unchanged. |
| Activation | `production_model_activation_service.py`, `production_rag_activation_service.py` | Production governance | Unchanged. A future router must NOT gain any new activation path — it only reads `production_visible`/approved-space state, never sets it. |
| Rollback | `production_rollback_service.py` | Production governance | Unchanged. |
| Production readiness | The entire Phase 15/15A `production_*` service set, the 48-batch canonical regression manifest, the readiness-report/acceptance pipeline | `backend/services/production_*.py`, `config/production_regression_manifest.json` | Phase 26 extends the manifest with new batches for new phases' tests, exactly as Phase 15A extended it — never forks a second regression system. |
| Admin Assistant approval lifecycle | `AdminAssistantService.propose()` → `review()` → `execute()`, `core_model/admin_assistant/action_registry.py`'s `ActionDefinition` model, `BLOCKED_ACTION_SUBSTRINGS` | `backend/services/admin_assistant_service.py`, `core_model/admin_assistant/` | Any new Admin Assistant actions for router/web/tool visibility (read-only inspection actions only, per the task's non-negotiable rules) must be registered the same way as the existing 71 — never a second action-execution mechanism. |
| Language localisation | `core_model/rag/language_routing.py`, `core_model/conversation/language_continuity.py` (chat-side); `admin_assistant_language_service.py`, `core_model/admin_assistant/language_preference.py` (Admin Assistant side) | As listed | Phase 17/21 extends `language_routing.py`'s classification and `language_continuity.py`'s continuity decision — it does not touch the Admin Assistant's isolated preference system, and vice versa. |
| Audit logging | `audit_logs` table, `AuditLogRepository`, used pervasively | `backend/database/schema.py`, `backend/database/repositories/` | Every new phase's mutating actions must audit through this, never a parallel log. |
| Backup encryption | `ProductionBackupEncryptionService`, `ProductionBackupEncryptionAssessmentService` (AES-256-GCM, Phase 15A) | `backend/services/production_backup_restore_readiness_service.py` | Unchanged; no future phase needs new encryption primitives. |
| Canonical regression | `ProductionRegressionService`, `config/production_regression_manifest.json` (v2, 48 batches) | `backend/services/production_regression_service.py` | Every future phase's tests are added as new manifest batches under existing or new categories — never a second regression runner. |
| SSRF-safe HTTP fetch | `dataset_verification_transport.py` (domain-allowlist, DNS/private-IP rejection, bounded size, MIME allowlist) | `backend/services/dataset_verification_transport.py` | Phase 20's trusted-web fetcher must extend or directly reuse this, never write a new raw `requests`/`httpx` call site (also independently enforced by the existing `test_no_production_service_imports_a_new_network_library` static guard pattern, Phase 15A). |
| External connector schema | `ExternalDataProviderConnector` Protocol + `BaseHttpConnector` | `backend/services/external_data_connectors/base.py` | Phase 20's web/MCP connectors should implement the same Protocol shape where it fits, for consistency, rather than a bespoke interface — evaluate case by case, but default to reuse. |
| Feedback taxonomy | `core_model/feedback/__init__.py` (`FEEDBACK_TYPES`, `CLASSIFICATION_CATEGORIES`, `SUBJECT_TYPES`) | `core_model/feedback/` | Phase 19/24 adds new enum values (`stale_information`, `source_conflict`, `unknown_question`) to the existing vocabulary — never a second feedback table/service. |
| Injection defense | `core_model/rag/injection_filter.py`, `core_model/conversation/injection_guard.py` | `core_model/rag/`, `core_model/conversation/` | Any new untrusted-content source (web pages, tool results, MCP responses) must be screened through this existing filter before entering a prompt, not a new ad hoc filter. |
